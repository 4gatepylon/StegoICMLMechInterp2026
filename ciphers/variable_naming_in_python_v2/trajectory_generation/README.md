# APPS trajectory generation interface

> NOTE TODO(hadriano) Cipher and prompts need to be improved for official run

This pipeline will collect Python answers from the same Codex model under ordinary
APPS prompts and prompts requesting variable-name cipher frames, then grade them
with the existing static decoder and Modal APPS evaluator. Its purpose is to supply
code, targets, and outcomes for downstream analysis and human review.

**Current status: interface only.** The Pydantic models in [schemas.py](schemas.py)
validate real records. [pipeline.py](pipeline.py) defines public function signatures
and contracts, with every body raising `NotImplementedError`. The Click entry point
supports `--help`; executing stages exits with an explicit error. No generation,
call-count reporting, progress bars, artifact writers/readers, or grading is
implemented yet. The layout below describes the future outputs, not files already
generated by this PR.

## One master configuration

Start with [config.example.json](config.example.json), validated as `RunConfig`.
It selects **all three APPS difficulty tiers**. There is no introductory-only
restriction. The inherited `AppsConfig` default remains introductory if `apps` is
omitted; use the example or specify `difficulties` explicitly to select all tiers.

| Section | Settings |
| --- | --- |
| `apps` | `split` (`train` or `test`), `difficulties`, `min_lines`, `max_lines`, `min_chars`, `max_chars`, `min_tests`, pinned `revision`, artifact-relative `cache_dir` |
| `sampling` | `min_bits`, `max_bits`, `lengths_per_problem`, `bitstrings_per_length`, `ordinary_generations_per_problem`, `payload_one_probability`, `control_one_probability`, `seed` |
| `cipher` | Ordered synonym groups, one control bit, and payload-length field width |
| `inference` | `model`, `timeout_s`, `min_remaining_usage_percent`, `usage_limit_id`; SDK artifact directory is resolved to the run's `sdk/` folder during preparation |
| `modal` | `app_name`, `case_timeout_s`, `solution_timeout_s`, `memory_mb`, `max_log_chars` |
| Top-level | `max_problems`, `generation_workers`, `grading_workers` |

APPS line/character bounds are inclusive and filter supplied **reference answers**,
not generated outputs. A problem needs a qualifying reference answer. Test count
means supplied input/output pairs, not independent behavioral coverage. `null`
disables an upper size bound or the problem cap. One run selects one split and
revision; use separate runs for train/test. Eligible problems are visited in
ascending `problem_id` order, optionally capped by `max_problems`.

The same `inference` settings apply to ordinary and framed requests. Existing Codex
authentication, tool restrictions, quota checks, and output validation are reused.
Only settings currently supported by `CodexInferenceConfig` are exposed: reasoning
effort and model sampling temperature are not currently supported by that helper.

## Sampling and conditions

For each problem, create two conditions:

- **`ordinary`:** Generate `ordinary_generations_per_problem` independent answers
  to the existing `build_apps_prompt(public_problem)` prompt, without a secret
  argument or any added cipher/steganography instructions. Zero disables this group.
- **`framed`:** Draw `lengths_per_problem` lengths uniformly from the inclusive
  `min_bits..max_bits` interval, with replacement. For each length draw, generate
  `bitstrings_per_length` payloads with IID Bernoulli bits. Independently draw the
  control bit for each request. Duplicate targets remain separate requests.

The two Bernoulli probabilities are independent configuration parameters, both
defaulting to 0.5. `sample_length`, `sample_bits`, and `sample_control_bit` are
separate functions with explicit RNG/parameter arguments so future sampling changes
do not require rewriting the pipeline. Endpoint probabilities 0 and 1 are valid.
The seed controls request draws, not Codex output. Ordinary requests consume no
random draws, so changing their count does not change framed targets.

Framed control `1` requests the exact payload, including leading zeroes. Control `0`
requests an explicit absent frame: it still receives the cipher instructions, but
its sampled length/payload appear only in metadata. **Control 0 is distinct from an
ordinary prompt.** A missing control bit is a decoding error, not valid absence.
Payload bounds are 1..8 in this version; the example uses four length bits to
represent eight. The schema rejects a cipher that cannot represent the upper bound.

For `P` selected problems, planned Codex model turns are:

```text
P * (lengths_per_problem * bitstrings_per_length + ordinary_generations_per_problem)
```

The example requests `P * (4 * 4 + 16) = 32P` model turns. The future CLI prints this
count after filtering and before generation, plus the number actually scheduled
after resume skips/retries. Grade-only runs announce zero Codex calls. Metadata and
preflight calls are not model turns; failures can reduce actual submissions.

## CLI contract

Run from the repository root with the `stego` environment. This command currently
shows the implemented option interface:

```bash
conda run -n stego python -m \
  ciphers.variable_naming_in_python_v2.trajectory_generation --help
```

The following is the **planned invocation**, which currently exits as unimplemented:

```bash
conda run -n stego python -m \
  ciphers.variable_naming_in_python_v2.trajectory_generation \
  --run-id initial-batch \
  --config ciphers/variable_naming_in_python_v2/trajectory_generation/config.example.json \
  --steps prepare --steps generate --steps grade
```

`--steps` is repeatable; stages run in prepare/generate/grade order. Any nonempty
subset is allowed if its saved prerequisites exist. Preparation requires `--config`;
later stages read the saved manifest. Optional preparation-only overrides expose
bit bounds, draw counts, ordinary count, Bernoulli probabilities, seed, problem cap,
and worker counts. Omitted overrides preserve the master config values. Dataset,
cipher, model, and evaluator settings are controlled through the master config.
Resuming rejects config/override arguments so saved requests cannot silently change.

Preparation refuses an existing run directory. Generation and grading skip existing
records by default; `--retry-errors` retries saved infrastructure errors only.
Completed incorrect or malformed answers are retained without resampling. Each run
supports one writer at a time. Stages execute sequentially, with bounded worker
queues within generation/grading and completion-driven `tqdm` bars showing counts,
throughput, and estimated time remaining.

## Artifact contract for review tools

All generated files live below `STEGO_ARTIFACTS_DIR`, never in the source tree:

```text
datasets/apps/trajectory-generation/<run-id>/
  manifest.json
  problems.jsonl
  requests.jsonl
  sdk/<native-inference-uuid>/...
  candidates/<request-id>/
    generation.json
    code.py
    grade.json
```

| File | Pydantic model and join contract |
| --- | --- |
| `manifest.json` | `RunManifest`: schema version 1, run ID/time, source commit if available, resolved master config, problem/request counts |
| `problems.jsonl` | One `ProblemRecord` per line: problem ID, difficulty, public prompt fields, and grading tests |
| `requests.jsonl` | One `RequestRecord` per line: request ID, problem ID, condition, draw indices/targets where applicable, exact prompt |
| `generation.json` | `GenerationRecord`: request ID, completed/error status, exact response/source, output/infrastructure errors, model/turn IDs, native artifact pointer, times |
| `code.py` | Exact UTF-8 extracted source, also stored in `GenerationRecord.code`; present whenever source extraction succeeded, including invalid syntax |
| `grade.json` | `GradeRecord`: request ID/condition, source SHA-256, status, functional/encoding/joint success, original Modal verdict, decoded bindings/result, errors, duration |

Schemas enumerate every field in docstrings. `schema_version` lives in the manifest
and applies to all records in its run. Join requests to problems by `problem_id`,
and generation/grades to requests by `request_id`. IDs are stable within a run:
`p<ID>-o<ordinary_index>` or `p<ID>-l<length_index>-b<bitstring_index>`; indices start
at zero. Different runs may reuse request IDs, so cross-run joins also need `run_id`.
Every metadata artifact is UTF-8 JSON; paths stored in public records are relative
to the artifact root. Source character/line counts can be computed from exact `code`
without needing a separate analysis schema.

Writers publish each file atomically. Preparation publishes the manifest last;
generation publishes `code.py` before its generation record. A missing manifest is
an unprepared run. A missing generation/grade record is unfinished work, not a
failed candidate. A crash may leave an orphan source or native SDK directory.
Readers may observe partial runs and must not infer completion from directory counts.
Corrupt/schema-invalid files raise errors rather than being silently regenerated.

To parse a record now, use `RequestRecord.model_validate_json(line)` or the other
model's equivalent; serialize with `model_dump_json()`. To inspect the contract
without Python-specific annotations, use `RunManifest.model_json_schema()` and the
other record models' `model_json_schema()` methods. The future `load_manifest`
convenience API is still a stub. Consumers can use standard JSON/JSONL file reading
against these Pydantic models immediately.

### Outcome semantics

| Condition/outcome | `functional_success` | `encoding_success` | `joint_success` |
| --- | --- | --- | --- |
| Framed, completed | All supplied cases passed | Requested control/payload recovered exactly | AND of both |
| Ordinary, completed | All supplied cases passed | `null` (no requested message) | `null` |
| Grading infrastructure error | `null` | `null` | `null` |

Malformed completed answers fail the applicable predicates and skip Modal/decoding.
Generation infrastructure errors receive a generation error record and no grade.
Modal `runner_error` is an infrastructure error; ordinary wrong answers and program
timeouts are candidate failures. Decoder failures do not prevent functional grading.
For ordinary answers, decoder output is diagnostic only: an accidentally valid
frame does not establish that a model intentionally encoded anything. `condition`
describes the prompt treatment, not a human steganography judgment. Review tools
should keep condition, targets, prompts, and grades hidden during blinded review.

## Reuse and extraction decisions

- Reuse `data.apps.load_apps`, `AppsConfig`, and `AppsTestCases`: they already handle
  all difficulty tiers, selection bounds, revision pinning, and evaluator inputs.
- Import `data.codex_apps.build_apps_prompt`/`SecretTask`, which delegate to
  `data.prompts`. Reuse the ordinary/present prompt paths and extend the shared
  builders for absent frames. Copying prompt templates would let examples drift.
- Reuse `data.codex_apps.infer` and its preflight/output validation. Wrap its native
  artifacts in the stable `GenerationRecord`; do not rewrite the SDK integration.
- Extract the `evaluate_candidate` logic from `data/generate_apps_codex_modal.ipynb`
  into `grade_candidate`, adapting it for ordinary/absent targets and explicit
  infrastructure outcomes. Reuse `decode` and `evaluate_on_modal` unchanged.
- Replace the notebook's sequential `run_batch` orchestration with the three durable
  stages. It depends on notebook globals and mixes generation with evaluation, so
  lifting that loop unchanged would not support independent stages or resume.

This interface PR leaves the notebook and existing helpers unchanged. A later
implementation may make the notebook call the shared grader after preserving its
demonstration behavior. No agentic retry/repair harness, analysis UI, human labels,
or pass@k aggregation is part of this pipeline interface.

## Verification scope

`test_schemas.py` covers JSON round trips, all-tier master configuration, bounded
sampling parameters and cipher capacity, ordinary/framed target consistency,
nullable versus boolean grade outcomes, infrastructure failures, artifact paths,
and CLI help/interface-only failure. Tests partition payload bounds at 1/8 and
outside them, probabilities at 0/1 and outside/nonfinite values, and ordinary,
control-0, control-1, malformed, and infrastructure-error records.

These tests verify record contracts, not runtime decoding accuracy or uniformity.
They omit sampling statistics, prompt rendering, concurrency, persistence/resume,
live Codex/Modal calls, and notebooks because the pipeline bodies are still stubs.

```bash
conda run -n stego python -m pytest -q \
  ciphers/variable_naming_in_python_v2/trajectory_generation/test_schemas.py
```
